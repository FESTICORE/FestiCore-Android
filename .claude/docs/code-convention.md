# 코드 컨벤션

포맷은 도구가 정하고, 사람은 이름과 주석만 신경 쓴다. 도구가 고친 결과와 다투지 않는다.

## 포맷

| 대상 | 도구 | 설정 | 고치기 | 검사 |
|------|------|------|--------|------|
| Kotlin · `*.kts` | ktlint 1.8.0 | `.editorconfig` (android_studio · 4칸 · 140자) | `gradle/format` | `gradle/format --check` |

- 버전은 `.mise.toml`에 고정한다(`mise install`).
- verify가 `format-kotlin`을 빌드보다 먼저 돌린다.
- 포맷만 바꾼 커밋은 기능 변경과 섞지 않는다.
- trailing comma를 쓴다. 매개변수가 2개 이상인 클래스, 3개 이상인 함수는 한 줄에 하나씩 쓴다.
- 테스트 함수 이름은 한국어를 백틱으로 쓴다(`` `만료 임박이면 요청 전에 갱신한다`() ``). 테스트 폴더는 ktlint 함수 이름 규칙을 끈다.
- 디자인 토큰 생성 파일은 포맷 검사에서 뺀다. 손으로 고치지 않고 FestiCore-DesignSystem에서 다시 만든다.

## return

- 블록 본문 함수면 `return`을 쓴다. 식 본문(`=`)은 한 줄 식이거나 `intent { }` · `withLock { }` · `try { }`처럼 블록 하나로 끝날 때만 쓴다. 여러 분기를 이어 쓰는 긴 식은 블록 본문 + `return`으로 쓴다.

## 이름

- 타입 · 파일은 PascalCase, 함수 · 변수는 camelCase. 약어도 단어처럼 쓴다(`Url`, `Api`).
- iOS와 같은 개념이면 같은 이름을 쓴다(UseCase · Repository · Entity, Intent ↔ `Action.View` 케이스).
- Bool은 `is` · `has` · `should`로 시작한다.

## 주석 (Hard)

꼭 필요한 주석만 단다. 코드가 말하지 못하는 것만 쓴다.

쓴다:
- 이유: 왜 이렇게 했는지, 더 단순해 보이는 방법을 왜 안 썼는지
- 제약: 바꾸면 깨지는 것(배포한 migration은 고치지 않는다, 키 이름을 바꾸면 값이 사라진다)
- 외부 계약: 서버 응답 형식처럼 코드 밖에서 정해진 값, iOS와 맞춰야 하는 값
- 보안 · 개인정보 주의

쓰지 않는다:
- 코드를 그대로 되풀이하는 설명, 문서 경로 안내, 변경 이력, 주석 처리한 코드
