# 시작 흐름 iOS 대조 점검 (온보딩 → 스플래시 → 첫 진입 로그인 → 가입 → 메인 탭)

## 목표

이미 옮긴 시작 흐름(PR #57 · #59 · #61 · #63 · #65)을 iOS 원본과 한 줄씩 다시 대조해 남은 차이를 고칠 목록으로 만든다. 기준은 `.claude/docs/ios-parity.md`(동작 · 문구 · 오류는 iOS, 구현은 이 저장소 규칙)이고, 설계 문서 `2026-11-21-launch-to-tabs-android-design.md`에 적힌 의도적 차이도 "지금 iOS와 같게 할 수 있는가"로 다시 따졌다.

- 근거는 모두 코드 `파일:행`이다. iOS 경로는 `../FestiCore-iOS/Projects/` 기준, Android 경로는 저장소 루트 기준이고 `.../`는 `src/main/kotlin/io/festicore/` 생략이다.
- 실행 · 스크린샷 · Figma 대조는 하지 않았다(아래 "확인 못 한 것").
- 분류: **버그**(옮겼지만 iOS와 다름) · **누락**(iOS에 있는데 Android에 없음) · **의도적 차이**(설계 문서나 커밋이 다르게 두기로 함) · **적응**(Android 플랫폼 관례라 맞음).
- Apple 로그인과 이후 단계로 미룬 범위(로그인 시트 · 기수 설정 · 딥링크 · 탭 내용)는 차이로 세지 않는다. 다만 시작 흐름 동작을 바꾸는 지점은 적었다.

줄 박스 차이(C1)는 화면별 표에 세 번 나오지만 원인이 하나라 버그 1건으로 셌다. 덮개 결과 · 401 전이에서 나온 것(버그 3: 로그인 직후 401 두 갈래 중 추가 1, Recheck 가입 중 만료, 홈 만료 · 재확인 401 / 누락 1: 포그라운드 때 Recheck 가입 덮개 재확인)은 "덮개 결과와 재확인 전이"에 있다.

가장 큰 차이는 화면 전환이다. Android의 두 `NavDisplay`에 `transitionSpec`이 없어 모든 화면 바꿈이 Navigation 3 기본값(700ms 크로스페이드)이고, Home 위 덮개는 애니메이션 없이 즉시 나타나고 사라진다. iOS는 스프링 · 슬라이드 · 0.3/0.35초 easeInOut을 화면마다 다르게 쓴다.

P2 구현 기록:

- 접근성: iOS `FestiCoreLottieView`(`FestiCoreLottieView.swift:55-61`)는 접근성 수정자를 붙이지 않고, `LottieAnimationView`(UIView)는 기본이 접근성 요소가 아니라 VoiceOver에 노출되지 않는다(실패 화면만 라벨이 있다). Android도 라벨을 두지 않는다(Compose `LottieAnimation`은 semantics가 없다). 정적 로고의 "FestiCore" 라벨은 없앴다.
- 시스템 스플래시 배경: DesignSystem은 Android 색 리소스(XML)를 생성하지 않고(`generated/android/tokens`는 Kotlin 3개), 테마 XML은 Compose 토큰을 읽지 못한다. 그래서 `app/src/main/res/values/colors.xml`의 `splash_background`에 staticInk 값을 두고, `SplashBackgroundColorTest`가 생성 토큰 `FestiCoreSemanticColor.staticInk`와 같은지 검사해 토큰이 바뀌면 실패하게 했다. 동기화 스크립트에 색 리소스 생성을 넣는 일은 DesignSystem 생성기 변경이라 이 PR 범위 밖이다.
- iOS와 남은 차이: 불러오기 실패 화면(경고 아이콘 + "애니메이션을 불러올 수 없습니다")과 원격 · `.lottie` 소스는 옮기지 않았다(앱 안 JSON만 쓴다).

## 덮개 결과와 재확인 전이 (Codex R1 · R2 · R3 반영)

결정 2 · 3을 그대로 구현하면 생기는 문제 세 가지를 iOS 근거로 정리한다. (1) 덮개를 닫고 재확인하는 순서와 대상(R1). (2) 가입 덮개가 반복되거나 재확인이 로그인 화면을 덮어쓰는 경우(R2). (3) 401일 때 계정 정리(R3).

### iOS가 덮개를 정하는 상태

- 상태 세 개: `presentation`(`launchLogin` · `onboarding`(가입) · `bearerSetup` · `login` 등), `isLaunchFlow`(첫 진입 화면에서 로그인했는지), `hasSession`(`Shared/AuthFlowState.swift:46,56-58`).
- 메인 탭을 덮는 조건 `coversMainTab`(`AuthFlowState.swift:78-89`): `presentation == .launchLogin`이면 덮는다. `isLaunchFlow`이면 가입 · 기수 설정 중과 로그인 직후 계정 확인 중(`isLoading`)에도 덮는다.
- 같은 가입 화면을 두 가지로 그린다(`AuthFlowState.swift:92-100`). 첫 진입 흐름이면 `showsLaunchSignUp`(로그인 화면 위에 그림, `MainTabView.swift:189-213`), 아니면 `showsSignUpCover`(메인 탭 위에 그림, `MainTabView.swift:104-122`).
- 재확인을 일으키는 곳은 두 곳뿐이다.
  - (a) `launchLogin`이 닫힐 때: `Main/AppCoordinator.swift:146-153`, `isLaunchLoginPresented`가 참에서 거짓이 될 때.
  - (b) 포그라운드: `Main/AppCoordinator.swift:243-250`.
  - 둘 다 `SessionCoordinator.foregrounded`(`Session/SessionCoordinator.swift:122-128`)를 거친다. 여기서 `presentation`이 로그인 계열(`acceptsLogin`)이거나 `bearerSetup`이거나 `isLoading`이면 아무것도 하지 않는다. 따라서 **재확인은 로그인 화면이 떠 있는 동안 실행되지 않아 로그인 화면을 덮어쓰지 않는다.**
- 로그인이 성공하면 `acceptLogin`(`Auth/AuthCoordinator.swift:455-477`)이 `isLaunchFlow = (presentation == .launchLogin)`, `presentation = nil`로 바꾸고 `beginRequest()`로 `isLoading = true`를 켠다. 이때 (a)가 일어나지만 `isLoading` 때문에 재확인은 하지 않는다. 로그인 직후 계정 확인은 `fetchProfile` 한 번뿐이다.
- 가입 제출(`AuthCoordinator.swift:487-520`) 결과는 `handleProfileUpdated`(`SessionCoordinator.swift:380-445`)가 받는다.
  - 가입 조건을 채웠으면 `finishEligible`로 `presentation = nil`이 되고 재확인하지 않는다. `presentation`이 `onboarding`에서 nil로 바뀌어 `isLaunchLoginPresented`는 변하지 않기 때문이다.
  - 못 채웠으면 "필수 정보가 확인되지 않았어요."를 보이고 가입 화면에 남는다.
- 가입 뒤로(`AuthCoordinator.swift:396-403` → `dismissFlow` `184-204`): 첫 진입 흐름이면 `launchLogin`, 아니면 `nil`로 간다. 확정된 세션은 유지한다.
- 포그라운드 때 가입 화면이 떠 있으면(`presentation == .onboarding`) iOS는 `presentation = nil` 뒤 재확인한다(`SessionCoordinator.swift:122-128`). 같은 계정이면 초안을 유지한 채(`reconcileSignUpDraft`, `:316-317`) 다시 `onboarding`을 띄운다(`:329-338`). 조건을 채웠으면 덮개를 닫는다.
- iOS가 `launchLogin`을 띄우는 곳은 세 곳뿐이다: 앱 시작(`Main/AppCoordinator+Route.swift:83-85`), 첫 진입 흐름 가입 뒤로(`AuthCoordinator.swift:195`), 첫 진입 흐름 중 세션 만료(`SessionCoordinator.swift:212-214`). 로그인 상태 홈에서 세션이 만료되거나 재확인이 401이면 `launchLogin`을 띄우지 않고 비로그인 메인 탭으로 둔다(`SessionCoordinator.swift:206-210,341-351`).

### Android 현재

- `LaunchLoginResult`는 `Completed` · `Skipped` 두 개다(`feature/auth/interface/.../LaunchLoginResult.kt:4-10`).
- `onLaunchLoginFinished`는 `launchLogin` · `signUp`만 지우고 재확인을 부르지 않는다(`app/.../app/navigation/AppCoordinator.kt:70-74`).
- `recheckProfile`은 덮개가 있으면 바로 돌아간다(`AppCoordinator.kt:130`). 그래서 덮개를 지우기 전에 부르면 아무 일도 하지 않는다.
- 테스트는 덮개가 닫힌 뒤 Home인지만 본다(`app/src/test/kotlin/io/festicore/app/navigation/AppCoordinatorTest.kt:219-227,240-255`). 재확인 호출 횟수와 세션 유지는 검사하지 않는다.
- 만료 이벤트(`AppCoordinator.kt:108-115`)와 재확인 401(`AppCoordinator.kt:155-161`)은 덮개 종류와 관계없이 `launchLogin = true`로 바꾼다. 테스트 `AppCoordinatorTest.kt:162,197,258`이 이 동작을 고정한다.
- 갱신 401이면 `TokenRefresher.kt:43-45`가 저장소를 지운 뒤 만료 이벤트를 먼저 보내고, 그다음 요청이 `NotAuthenticated`로 실패한다. iOS도 같은 순서다: `Service/FestiCoreAuth/Sources/FestiCoreAuth.swift:234-237`이 알림을 보낸 뒤 실패를 돌려주고, 늦게 온 프로필 결과는 세대 검사로 버린다(`SessionCoordinator.swift:183,199`).

### 결과 타입과 순서 규칙

`LaunchLoginResult`를 넷으로 나눈다. 덮개를 연 흐름의 출발점(`origin`)은 `AppCoordinatorState`로 알 수 있다. `launchLogin == true`이면 첫 진입(Launch), `signUp != null`이면 재확인(Recheck)이다.

| 결과 | 보내는 곳 |
| --- | --- |
| `Completed` | 로그인 직후 계정 확인 통과(`LaunchLoginViewModel.kt:87-89`), 가입 완료(`SignUpViewModel.kt:135,155`) |
| `Skipped` | launchLogin "지금은 건너뛸게요"(`LaunchLoginViewModel.kt:33-36`) |
| `SignUpCancelled` | 재확인으로 뜬 가입의 뒤로. 첫 진입 흐름 안의 가입 뒤로는 결과를 올리지 않고 auth 스택에서 pop한다(N7) |
| `SessionLost(expired: Boolean)` | 401. `expired`는 이 시도 중 만료 이벤트가 있었는지 |

규칙:

1. **덮개 상태를 먼저 바꾸고 그다음 재확인한다.** `onLaunchLoginFinished`에서 같은 `intent` 안에서 `reduce { launchLogin = false; signUp = null }`을 한 뒤 `recheckProfile()`을 부른다. 이렇게 해야 `AppCoordinator.kt:130` 검사를 통과한다.
2. **재확인은 Launch 출처의 `Skipped`에서만 한다.** iOS (a)와 같다. `Completed`는 이미 확인을 마쳤다(iOS `isLoading` 검사와 같은 의미). `SignUpCancelled`과 `SessionLost`는 iOS에서 `isLaunchLoginPresented`가 바뀌지 않으므로 재확인하지 않는다.
3. **재확인은 로그인 화면을 덮어쓰지 않는다.** `recheckProfile`은 `launchLogin == true`이면 실행하지 않는다(지금처럼). 재확인 결과가 가입 조건 미달이면 늘 Recheck 출처의 `signUp` 덮개만 만든다. `launchLogin`은 위 iOS 세 경우(시작 · Launch 가입 뒤로 · Launch 흐름 중 만료)에서만 켠다.
4. **같은 가입 덮개를 연달아 다시 만들지 않는다.** 가입 덮개는 덮개가 닫힌 뒤 재확인 한 번이나 포그라운드 한 번마다 최대 한 번 뜬다. 포그라운드 때 가입 화면이 떠 있으면(Recheck 덮개, 또는 Launch 덮개 안의 가입 화면) iOS처럼 재확인한다. 조건을 채웠으면 덮개를 닫고, 같은 계정이 여전히 미달이면 덮개 · 화면을 새로 만들지 않고 그대로 둔다(초안 유지, iOS `SessionCoordinator.swift:316-317`). launchLogin 화면이 보이면 재확인하지 않는다(iOS `acceptsLogin` 검사, `:124`). 그래서 `recheckProfile`의 "덮개가 있으면 반환" 조건(`AppCoordinator.kt:130`)을 "launchLogin 화면이 보이면 반환"으로 좁힌다. 가입 화면이 보이는지는 auth Coordinator가 맨 위 경로를 상위에 알려 판단한다.
5. **401은 성공 · 건너뛰기와 따로 처리한다.** 아래 "401 전이"를 따른다.

## 쟁점

1. **Lottie 도입(P2)** — 새 의존성 `com.airbnb.android:lottie-compose`(Apache-2.0)는 라이선스 승인 대상이다(CLAUDE.md 12). 추천: 승인받아 도입한다. iOS도 같은 계열(`lottie-spm` 4.5.2, iOS `Tuist/Package.swift:87`)이고 같은 JSON을 그대로 쓸 수 있다. 승인 전에는 P2의 나머지(배경색 · 시작 시점 · 태그)만 먼저 낸다.
2. **가입 뒤로 시 세션** — 결정 2(iOS와 같게)로 정했다. 구현 순서 · 반복 방지 규칙은 "덮개 결과와 재확인 전이"를 따른다. iOS도 가입 덮개는 덮개가 닫힐 때 한 번, 포그라운드마다 한 번만 다시 뜬다.
3. **로그인 직후 프로필 401** — 결정 3(덮개 닫기)은 만료 이벤트가 없는 401에만 맞는다. 갱신 401(만료 이벤트 있음)이면 iOS는 첫 진입 흐름이라 launchLogin을 다시 띄운다(`SessionCoordinator.swift:212-214`). 추천: 두 갈래로 나눠 iOS와 같게 한다(전이 절 401 표).
4. **약관 상세 앱 안 화면(P4b)** — 새 라이브러리 없이 `android.webkit.WebView`로 가능하다. 추천: 지금 옮긴다(`feature/web` 모듈 신설, iOS `Feature/Web`과 같은 이름). 외부 링크 · 다운로드 정책은 iOS `WebNavigationPolicy.swift`를 대조한 뒤 정한다.
5. **라이브 탭 루트 탭 바** — 빈 탭 화면에서 숨기면 탭을 바꿀 수 없다. 추천: 축제 목록 PR에서 함께.
6. **분석 이벤트** — `service/analytics`가 없어 지금 같게 못 한다. 추천: 그 모듈 단계로 유지.
7. **홈에서 세션 만료 · 재확인 401 때 launchLogin** — iOS는 첫 진입 흐름이 아니면 launchLogin을 띄우지 않고 비로그인 메인 탭으로 둔다(`SessionCoordinator.swift:206-214,341-351`). Android 설계 수용 기준 4 · 5와 `AppCoordinator.kt:113,160`은 launchLogin을 띄운다. 추천: 사용자 지시("iOS와 같게")대로 iOS를 따르고, 설계 문서 수용 기준과 테스트 `AppCoordinatorTest.kt:162,197,258`을 P4에서 같이 고친다.

## 확인 못 한 것

- 에뮬레이터 · 실기기 실행, 스크린샷 · 화면 녹화 비교, Figma 대조를 하지 않았다. 모든 차이는 코드 근거이고 눈으로 본 크기 차이는 없다.
- C1 차이의 실제 크기(Pretendard 글꼴 고유 줄 높이 대비 토큰 줄 높이)는 재지 않았다.
- SwiftUI `.buttonStyle(.plain)`의 눌림 · `.disabled` 시각 변화(launchLogin 진행 중 버튼이 흐려지는지)와 Android에 비활성 표현이 없는 것이 실제로 다르게 보이는지.
- SwiftUI 페이지 `TabView`의 선택 값이 바뀌는 시점과 Compose `PagerState.currentPage`(스와이프 중간에 바뀜)가 같아 점이 같은 순간에 바뀌는지.
- SwiftUI `easeInOut` · `spring(response:dampingFraction:)`의 정확한 곡선. 위 대응은 흔히 쓰는 근사(베지어 0.42/0.58, stiffness = (2π/response)²)다.
- Navigation 3 1.2.1에서 스택을 같은 길이로 바꿔 끼울 때 `transitionSpec`과 `popTransitionSpec` 중 무엇이 쓰이는지, pop 때 나가는 화면이 위에 그려지는지(N7). 바이트코드로는 기본값만 확인했다.
- `Splash.json`(내장 PNG 9개)이 lottie-android에서 iOS와 같게 그려지는지(이미지 레이어 · 마스크 지원).
- iOS `FestiCoreLottieView`의 VoiceOver 노출 여부. Android 정적 스플래시는 로고에 "FestiCore" 라벨이 있다(`SplashScreen.kt:38`). Lottie로 바꿀 때 iOS와 같게 할지 확인이 필요하다.
- iOS `WebNavigationPolicy.swift`와 `WebFeature.swift`의 세부(외부 링크 처리 · 재시도 규칙)는 읽지 않았다(P4b에서 대조).
- iOS에서 만료 알림(`FestiCoreAuth.swift:237`)이 `AsyncStream`을 거쳐 `sessionExpired`로 처리되는 것이 늦은 `profileLoaded`보다 항상 먼저인지는 실행해 보지 않았다. 알림이 먼저 나가고 결과는 세대 검사로 버려진다는 코드 근거(`SessionCoordinator.swift:183,199`)로 판단했다.

## 결정 (호스트, 2026-11-21 — 사용자 지시 "묻지 말고 iOS와 같게")

1. Lottie: `lottie-compose`(Apache-2.0) 도입, iOS `Splash.json`을 그대로 쓴다(P2).

7. 첫 진입 흐름이 아닐 때의 세션 만료 · 재확인 401: iOS와 같게 launchLogin을 띄우지 않고 비로그인 메인 탭에 둔다. launch-to-tabs 설계 수용 기준 4 · 5와 `AppCoordinatorTest.kt:162,197,258`을 P4에서 함께 고친다.

5. 라이브 탭 루트 탭 바 숨김: FestivalList F4 PR에서 함께 처리한다.
6. 분석 이벤트: `service/analytics` 모듈 단계로 미룬다.
