## 목표

iOS 기수 기능을 Android로 옮긴다. 기수는 페스티벌 현장에서 깃발을 들고 사람들을 이끄는 사용자다. 사용자가 보는 것은 아래가 전부다.

1. **기수 진입** — 마이 탭 "기수이신가요?" 카드(`FCBearerPrompt`) · "다른 페스티벌 깃발 만들기", 가입 직후 "페스티벌에서 깃발을 드시나요?", 라이브 보드 상단 "기수" 버튼, 마이 "내 깃발" 카드.
2. **기수 여부(RoleChoice, S14 C)** — 가입 직후에만. "관객이에요" / "기수예요".
3. **깃발 등록(Register, S14 D · E)** — 코드 없이 페스티벌을 고르고 깃발 프로필(이름 · 소개 · 사진 · 태그 · 존 · 계획 공개)을 만든다. 저장 완료 화면에서 팩 받기 또는 공동 기수 초대.
4. **기수 인증(Claim, S13 F~I)** — 운영팀(또는 원래 기수)이 준 6자리 코드로 기존 깃발의 기수가 된다. 3번 틀리면 10분 잠금.
5. **깃발 프로필(Profile, S10)** — 프로필 수정 · 사진 업로드(진행률 · 취소) · 공동 기수 초대 코드 · 저장 완료.
6. **오늘 계획 고르기(PlanPick)** — 받은 팩의 공연을 날짜별로 골라 깃발 "오늘 계획"으로 저장(프로필 저장 때 보냄).
7. **기수 보드(Board, S09)** — 다크 고정 화면. 깃발 올리기 · 존 이동 · 활동 변경 · 쉬는 중 · 오늘 종료 · 다시 시작. 누르면 바로 반영하고 오프라인이면 기기에 남겨 순서대로 다시 보낸다.

시각(수치 · 문구 · 토큰 · 에셋 · 접근성)은 iOS View와 같게, 플랫폼 관례(사진 선택 · 뒤로 · 키보드 · 햅틱 · 파일 저장)는 Android 방식을 따르고 "iOS → Android 적응" 표에 적는다.

이 문서가 만들지 않는 것: 잠금화면 대표 깃발 고르기 화면(`Profile/LockScreen` · `PinnedFlagPicker`, 마이 탭 설계 M5 · 깃발 설계 F4-1 — 라이브 액티비티 단계, 경계 절), 기수 모드 켜기 · 끄기(`PUT me/bearer-mode`, iOS에 호출 없음), `FCBearerChoiceSheet`(쟁점 B8).

## 수용 기준

1. 로그인한 마이 탭에 내 깃발이 없으면 기수 카드("깃발 프로필을 만들면 바로 기수로 시작해요")가, 있으면 "내 깃발" 카드(깃발 줄 · "기수 보드 열기" · "다른 페스티벌 깃발 만들기")가 보인다. 비로그인이면 둘 다 없다.
2. 기수 카드 → 깃발 등록이 마이 스택에 push되고(탭 바 숨김), 받은 팩 · 앞으로 열리는 페스티벌 목록에서 고르고 저장하면 저장 완료(팩 있으면 E2, 없으면 E1)가 보인다. 같은 내용을 다시 보내면 같은 `Idempotency-Key`로 보낸다.
3. "공동 기수 초대 코드가 있어요" → 기수 인증. 코드 칸은 I · O · 0 · 1을 빼고 대문자 6자리만 받고, 틀리면 남은 횟수, 잠기면 `m:ss` 카운트다운이 iOS 문구대로 보인다. 성공하면 깃발 프로필 → 저장 완료 → 기수 보드로 이어진다.
4. 깃발 프로필에서 Android Photo Picker로 고른 사진이 JPEG(긴 변 2048 이하 · 5MB 이하 · 짧은 변 256 이상)로 다시 인코딩되어 EXIF(위치 포함) 없이 올라가고, 진행률 · 취소 · 실패 문구가 iOS와 같다. 권한 요청 창이 뜨지 않는다.
5. 라이브 보드 "기수" 버튼과 마이 "기수 보드 열기"가 같은 기수 보드를 연다. 보드는 시스템 다크 설정과 관계없이 다크이고, 누른 변경이 1초 확인 오버레이와 함께 바로 반영된다. 오프라인이면 "연결되면 팔로워에게 알려요"와 대기 건수가 보이고, 연결되면 누른 순서대로 보낸다. 보드를 닫거나 앱을 다시 켜도 대기열이 남는다. 다른 계정으로 바뀌면 이전 계정 대기열은 보내지 않고 버린다.
6. 보낼 것이 남은 채 닫으면(상단 "관객 화면으로" · 시스템 뒤로) "아직 보내지 못한 변경이 N건 있어요" 확인이 뜬다.
7. iOS 기수 테스트(아래 PR 묶음 표)가 같은 이름의 Android 테스트로 옮겨져 통과하고, `./gradlew testStageDebugUnitTest assembleStageDebug` · `.claude/scripts/verify` 통과. 에뮬레이터 확인(사진 선택 · 다크 고정 · 오프라인 대기열)은 별도로 보고한다.

## 상태 대기열 (`outbox/`, `BOX`)

- 앱 범위 싱글턴 하나(`BearerLiveDependencies.swift:15-18`). 보드를 닫아도 이어 보낸다. Android는 Koin `single` + 앱 범위 `CoroutineScope`(설계 E7 `UserNotificationBadgeUseCase`와 같은 방식), 상태 보호는 `Mutex`(iOS `actor`).
- 넣기(`BOX:54-62`): 누른 시각 순서로 끼워 넣되 이미 한 번 보낸 맨 앞 건 앞에는 넣지 않는다. 넣을 때마다 파일에 저장하고 `Pending` 알림 · 작업 시작.
- 보내기(`BOX:107-162`): 맨 앞 건부터 한 건씩. 현재 사용자 없음 → `NeedsLogin` 멈춤. 맨 앞 건 주인이 현재 사용자가 아니면 **주인이 현재 사용자가 아닌 건만** 버리고(현재 사용자 건은 남긴다, `BOX:117-125` `removeAll { $0.ownerUserID != currentUserID }`) 다시 고른다. 성공 → 지우고 `Sent`. `Offline` → 알리고 5초 뒤. `RateLimited` → 15초 뒤. `NotAuthenticated` → `NeedsLogin` 멈춤(대기열 유지). `TermsRequired` → `GaveUp` 멈춤. 그 외 `BearerError`(`Unavailable` · `InvalidResponse` 제외) → 그 깃발 대기열을 모두 버리고 `Rejected`. 나머지 → 2 · 4 · 8 · 16 · 32초 뒤, 5번 넘으면 `GaveUp`.
- **계정 격리 · 세션 묶기.** iOS는 건마다 주인(`ownerUserID`)을 저장하고, 전송 직전에 현재 사용자를 확인한 뒤 저장소가 그때의 세션 ID를 다시 읽어 `sessionBound(sessionID)`로 보낸다(`BOX:110-128`, `BRI:170-177 · 198-203`). `sessionBound`는 다른 로그인 토큰으로 나가지 않는다(`iOS/Core/FestiCoreNetwork/Interface/Auth/FestiCoreAuthorization.swift:14-15`, 테스트 `sessionBoundRequestRejectsNewAccount`). 다만 "사용자 확인"과 "세션 읽기"가 따로라 그 사이에 계정이 바뀌면 이전 사용자 건이 새 세션으로 나갈 틈이 있다. Android는 안전한 쪽으로 정한다(iOS와 다른 점):
  1. 한 건을 보내기 전에 `currentSessionId()`로 세션 `S`를 먼저 읽고, 그다음 현재 사용자 `U`를 읽고, 다시 `currentSessionId() == S`인지 확인한다. 셋 중 하나라도 어긋나면 보내지 않고 처음부터 다시 고른다(사용자가 없으면 `NeedsLogin`).
  2. 건의 주인이 `U`일 때만 그 건을 `bearerAuthorization(expectedSessionId = S)`로 보낸다. 세션이 바뀌면 인증 플러그인이 보내지 않고 `AuthSessionError.NotAuthenticated`를 던진다(`service/auth/sources/.../FestiCoreAuthPlugin.kt:23`) → 그 건은 지우지 않고 `NeedsLogin`으로 멈춘다. 응답 처리는 결과가 확정됐는지로 나눈다(Codex R2 B-5): (가) 2xx를 받았으면 서버가 `S`(= 주인 `U`의 세션)로 이미 반영했으므로 건을 지운다. 이때 세션이 `S`가 아니면 결과(`Sent` 상태)를 보드에 알리지 않는다. (나) 계정 변경으로 작업이 취소됐거나 전송 실패 · 시간 초과처럼 서버 반영 여부를 모르면 건을 지우지 않고 원래 주인 건으로 남긴다. 주인이 다시 로그인하면 같은 건을 다시 보낸다.
  - 다시 보내도 중복 반영되지 않는 근거: 서버는 `(userId, Idempotency-Key)`로 응답을 24시간 보관해 같은 본문이면 저장한 응답을 돌려주고, 다른 본문이면 409 `IDEMPOTENCY_CONFLICT`다(`../FestiCore-Backend/src/modules/flags/flags.service.ts:199-223 · 245`). 24시간이 지나도 서버는 마지막으로 반영한 `clientAt`과 비교해, 같은 `clientAt` · 같은 상태면 반영 없이 현재 상태를 돌려주고(`flag-rules.ts:301-310` `repeatsAppliedStatus`, `flags.service.ts:1084-1099`), 더 이른 `clientAt`이면 409 `STATUS_STALE`로 거절한다(`flag-rules.ts:177-181`). 대기열은 같은 멱등키 · 같은 `clientAt`을 파일에 그대로 보관해 다시 보낸다(`BOR:11-19`, iOS와 같음). 그래서 결과 불명 건을 다시 보내는 것은 안전하다.
  3. 주인이 `U`가 아닌 건은 보내지 않는다. iOS는 이 건을 버리지만(`BOX:117-125`, 테스트 `dropsOtherAccount`) Android는 남겨 두고 주인이 다시 로그인하면 이어 보낸다(Codex R2 B-5, iOS와 다른 점). `pending` · 보드 표시에는 현재 사용자 건만 보인다. 남겨 둔 건은 아래 "만료" 규칙으로 정리되고, 주인이 탈퇴에 성공하면 `AccountCoordinator`가 그 사용자 건을 지운다.
  4. 계정이 바뀌면(로그아웃 · 탈퇴 · 다른 계정 로그인 · 세션 만료, `AppCoordinator` 현재 사용자 변경) 대기열 작업을 취소하고, 다음 재개 때 1~3번 규칙으로 다시 고른다. 마이 탭 설계 A1 계정 작업의 세대 · 세션 확인과 같은 방식이다.
  5. 테스트: iOS `dropsOtherAccount`는 Android에서 `keepsOtherAccountUntilOwnerReturns`로 바꿔 옮기고, Android 추가 `keepsCurrentUserItemsWhenOtherOwnerFirst` · `sessionChangeBeforeSendDoesNotSend` · `confirmedSendAfterSessionChangeIsRemovedSilently` · `unknownResultAfterAccountChangeIsKeptForOwner` · `resendUsesSameKeyAndClientAt` · `withdrawalRemovesOwnerItems`.
- **만료(오래된 변경 폐기).** iOS 대기열에는 만료가 없다(`BOX` 전체, 시간 기준 삭제 없음). 기수 상태는 하루 단위이고(`BE` `BearerFlag.swift` "깃발의 하루 상태", 재시작 KST 하루 한 번 `BearerStatusChange.swift`), 서버는 마지막 반영 `clientAt`보다 늦은 변경이면 날짜가 지나도 받아들인다(`flag-rules.ts:177-181`). 그래서 어제 오프라인에서 누른 "종료"가 오늘 나가 오늘 깃발을 내릴 수 있다. Android는 기준을 더한다(Codex R2 B-6, iOS와 다른 점):
  1. "지금"은 기기 시각이 아니라 아래 "시계 오차"의 서버 시각 추정값이다. 건의 `clientAt`이 지금과 서울 날짜(`AppDateFormat.timeZone`)가 다르면 보내지 않고 버린다. 날짜가 같아도 24시간(서버 멱등 보관 기간)을 넘으면 버린다 — 같은 날이면 실제로는 생기지 않지만 기기 시각이 바뀐 경우를 막는다.
  2. 검사 시점: 파일을 읽을 때 · 한 건을 고를 때마다. 버리면 `Pending` 알림을 보내고, 보드가 그 깃발을 보고 있으면 최신 상태를 다시 읽는다(`Rejected`와 같은 처리, 문구 "바꾸지 못해 최신 상태로 돌렸어요").
  3. 주인이 돌아오지 않은 다른 계정 건(3번)도 같은 규칙으로 하루가 지나면 사라진다. 기기에 남는 개인 정보(깃발 · 존 · 사용자 ID)의 보관 기간을 하루로 묶는 효과도 있다.
  4. 테스트: `dropsItemsFromPreviousSeoulDay` · `dropsItemsOlderThan24Hours` · `expiryOnLoadNotifiesPending`.
- **시계 오차(Codex R3 B-7).** iOS는 `clientAt`을 기기 시각 그대로 만들고(`BUI:96-98` `date.now`) 서버 시각 보정이 없다(`BD` · `B`에서 서버 시각 · `Date` 헤더 사용 0건). 서버는 `clientAt`이 서버 시각보다 5분 넘게 미래면 400 `VALIDATION` "clientAt이 미래입니다."로 거절한다(`../FestiCore-Backend/src/modules/flags/flag-rules.ts:171-176`). iOS는 400을 `InvalidRequest`로 바꾸고(`BRI:247`), 대기열은 이를 "서버가 받지 않는 변경"으로 보아 그 깃발 대기 건을 모두 버린다(`BOX:145-151`). 그래서 기기 시계가 5분 넘게 앞서 있으면 첫 변경이 거절되고 뒤이은 오프라인 변경까지 사라진다. 만료 판단도 기기 시각이라 오차만큼 틀어진다. Android는 보정한다(iOS와 다른 점):
  1. 서버 시각 추정: `domain/bearer/sources`가 `BearerServerClock`(오프셋 = 서버 `Date` 헤더 − 응답을 받은 기기 시각)을 둔다. 기수 저장소의 모든 응답(2xx · 오류 모두, `festiCoreExchange`로 헤더를 읽음)에서 갱신한다. stage 응답에 `Date` 헤더가 있다(2026-11-24 `GET me/bearer-flags` 401 응답 `date: Tue, 24 Nov 2026 08:59:28 GMT`, 기기 UTC와 같은 초). 헤더 정밀도는 1초라 서버 허용치 5분에 비해 충분하다. 오프셋은 메모리에만 두고, 모르면 0(iOS와 같은 동작). 라이브 보드의 `LiveBoardPresentation.serverNow(serverAt, anchor, now)`(`feature/festival`, 라이브 응답 `serverAt` 기준)와 같은 생각이지만 feature 계층이라 domain이 쓸 수 없고 기수 응답에는 `serverAt`이 없어 따로 둔다.
  2. `makeStatusRequest`의 `clientAt` = 기기 시각 + 오프셋. 만료 · 서울 날짜 판단도 같은 추정값을 쓴다.
  3. 미래 시각 거절 구분: 상태 전송이 400이면 그 응답의 `Date` 헤더로 판단한다. `건 clientAt > 응답 Date + 5분`이면 시계 오차로 본다(서버 오류 코드는 다른 형식 오류와 같은 `VALIDATION`이라 코드로는 못 가르고, 메시지 문자열에 기대지 않는다). 이때는 버리지 않고 (가) 오프셋을 그 응답으로 갱신하고 (나) 그 깃발 대기 건 중 이 기기에서 만든 건(파일의 모든 건)의 `clientAt`에서 `건 clientAt − 응답 Date`만큼을 빼 순서 · 간격을 유지한 채 다시 쓰고 (다) 파일에 저장한 뒤 같은 멱등키로 다시 보낸다. 다시 쓴 값이 조정 전 서버가 마지막으로 반영한 시각보다 이를 수 있는데, 그러면 서버가 `STATUS_STALE`로 거절해 기존 `Rejected` 처리(최신 상태 다시 읽기)로 끝난다.
  4. 같은 멱등키로 본문(`clientAt`)을 바꿔 보내도 되는 근거: 서버는 멱등 응답을 성공 경로 끝에서만 기록하고(`flags.service.ts:1150` `remember`), 400은 그보다 앞 `nextStatus`(`flags.service.ts:1101`, `flag-rules.ts:147 · 171-176`)에서 트랜잭션째 던져 기록이 남지 않는다. 그래서 400 뒤 바뀐 본문은 `IDEMPOTENCY_CONFLICT`가 되지 않는다. 결과를 모르는 건(취소 · 시간 초과)은 본문을 바꾸지 않는다(이미 기록됐을 수 있음).
  5. 다시 쓰기는 한 건에 한 번만 한다. 다시 보낸 뒤 또 400이면 iOS처럼 `Rejected`로 끝낸다(무한 반복 방지).
  6. 그 외 400(형식 오류)은 iOS와 같이 `Rejected`.
  7. 테스트: `clientAtUsesServerClockOffset` · `futureClientAtRewritesAndResendsWithSameKey` · `futureClientAtKeepsLaterOfflineItems` · `secondFutureRejectionDropsAsRejected` · `nonClockValidationStillRejects` · `expiryUsesServerClock`.
- `pending(flagId)`: 현재 사용자 건만(`BOX:64-68`). `events(flagId)`: 깃발별 구독(Android `SharedFlow` 필터 또는 구독자 목록 + `callbackFlow`). `resume()`: 읽고 작업 시작.
- **재개 시점.** iOS는 보드가 보일 때(`BBF:314-324`)와 "다시 보내기"(`BBF:231-234 · 333-336`)에서만 `resume`을 부른다. 앱 · 내비게이션에서 부르는 곳이 없다(`App` grep 0건). 넣은 뒤에는 작업이 앱이 살아 있는 동안 이어지지만(`BOX:102-105`), 앱을 다시 켠 뒤 보드를 열지 않으면 대기 건이 나가지 않는다. Android는 이 구멍을 막는다(iOS와 다른 점, 쟁점 B4 결정):
  1. `resume`을 부르는 곳: 보드가 보일 때 · "다시 보내기"(iOS와 같음) + 앱 시작 뒤 현재 사용자가 확인됐을 때(`AppCoordinator`가 현재 사용자를 정한 직후) + 로그인으로 현재 사용자가 생겼을 때 + 네트워크가 다시 연결됐을 때(`ConnectivityManager` 콜백, 대기 건이 있을 때만).
  2. 보이는 것: 보드 밖에서는 아무 표시도 하지 않는다(iOS도 보드 밖 표시가 없다). 보드를 열면 남은 건수(`FCBearerFooter`) · 오프라인 배지 · 멈춤 문구가 iOS 문구 그대로 보인다. 마이 "내 깃발" 카드에는 표시를 더하지 않는다.
  3. 멈춤(`NeedsLogin` · `GaveUp`)은 자동 재개 대상이 아니다. 로그인 뒤 재개(1번)와 "다시 보내기"로만 이어 간다(iOS `BearerOutboxEvent.needsLogin` · `gaveUp` 주석과 같음, `BE` `BearerOutboxEvent.swift`).
  4. 테스트: `resumesAfterLaunchWhenUserKnown` · `resumesOnLogin` · `doesNotResumeWithoutUser`.
- 파일(`BOX:44-51 · 181-204`, `BOR`): iOS `Application Support/bearer-status-outbox.json`, 원소 `{flagID, ownerUserID, idempotencyKey, clientAt, kind, zoneID, activity}`. 주인이 없거나 `kind` 조합이 틀린 원소는 읽지 않는다(`BOR:42-55`). 읽기 · 쓰기 실패는 오류 종류만 로그(멱등키 · 존 · 깃발 ID는 남기지 않음)하고 메모리 대기열로 계속. Android 저장 방식은 쟁점 B3.

- 비로그인: 기수 카드 · 내 깃발 카드 없음, 라이브 보드 "기수" 버튼 없음(`LBC:113-114`). "다른 페스티벌 깃발 만들기" 등 기수 흐름 요청이 세션 없이 오면 로그인 시트를 연다(`MTCSc:354-356`). 흐름 안에서 세션을 잃으면 흐름을 닫는다(iOS `sessionChangeClosesBearerFlows`), 같은 세션이면 유지(`sameSessionKeepsBearerFlows`).

## 위험

- **API 26-27 HEIC**: 이 버전은 HEIF를 디코딩하지 못해 HEIC 사진이 "이 사진은 올릴 수 없어요" 문구로 끝난다. Photo Picker는 HEIC도 보여 준다. minSdk 26 사용자 비율을 확인하지 못했다.
- **큰 사진 메모리**: 원본 크기 그대로 디코딩하면 OOM이 날 수 있다. 크기를 먼저 읽고 `inSampleSize` · `setTargetSize`로 줄여 디코딩해야 한다.
- **업로드 제한 시간**: OkHttp 기본(연결 · 읽기 · 쓰기 각 10초)은 쓰기 한 번 단위라 5MB 업로드 자체는 끊기지 않을 수 있지만 iOS 60초 총 제한과 다르다(쟁점 B5).
- **대기열 자동 재개**: iOS는 앱을 다시 켜고 보드를 열지 않으면 대기 건이 나가지 않는다. Android는 앱 시작 · 로그인 · 연결 복구에서도 재개한다(대기열 절 "재개 시점"). 그 결과 보드를 보지 않는 동안 오래된 변경이 늦게 나갈 수 있다 — 서버가 `clientAt` 기준으로 오래된 변경을 409로 거절하면(`BEF:439-519`) 그 깃발 건을 버리고 다음 보드 진입 때 최신 상태를 읽는다.
- **같은 계정 다른 기기**: 서버 409 `STATUS_STALE`가 오면 대기열의 그 깃발 건을 모두 버린다(iOS 동작). 오프라인에서 누른 여러 건이 한꺼번에 사라질 수 있다.
- **`FlagProfileBody` 직렬화**: 키마다 null 명시 · 생략이 달라 기본 `FestiCoreJson` 설정에 맡기면 서버가 400(미허용 · 빈 요청) 또는 소개 · 존을 지우지 못한다. MockEngine 본문 비교 테스트로 막는다.

## 쟁점 (추천안 포함)

- **B1 가입 직후 기수 여부.** iOS는 가입 완료(`signUpCompleted`) 때 가입 스택에 기수 여부를 push한다(`MTCSc:410-413`, `AuC:219-224`). Android `LaunchLoginResult.Completed`는 로그인과 가입을 구별하지 않는다. (a) `Completed`에 가입 여부(예: `signedUp: Boolean`)를 더하고 가입 덮개를 닫기 전에 기수 흐름을 같은 덮개 위에 잇는다(추천, iOS 흐름 그대로, BC2로 분리해 마이 연결과 섞지 않음). (b) 가입 직후는 묻지 않고 마이 기수 카드만 둔다 — 첫 기수 유입 경로가 iOS와 달라진다.
- **B2 EXIF 방향 · 테스트.** (a) API 28+는 `ImageDecoder`, 26-27은 `BitmapFactory` + 플랫폼 `android.media.ExifInterface`(InputStream 생성자, API 24+)로 회전하고, 메타데이터 제거 · 방향은 Robolectric 단위 테스트로 확인한다(추천, 새 의존 없음). Robolectric의 `ImageDecoder` · `Bitmap.compress` 지원 범위가 모자라면 그 2건만 계측 테스트로 돌린다. (b) `androidx.exifinterface` 추가 — 기기별 EXIF 버그 보정이 낫지만 의존이 늘고 라이선스 확인(사람 몫)이 필요하다.
- **B3 대기열 저장 방식.** (a) `filesDir/festicore/bearer-status-outbox.json`에 `AtomicFile`로 원소 목록 JSON(iOS 파일 형식 그대로, 기존 `PackCache` · `FestivalCatalogCache`와 같은 방식, 추천). 경로(`File`)는 app이 Koin으로 넘겨 `domain/bearer/sources`가 `Context`를 직접 받지 않는다. (b) Room — 건수가 적고(분당 12회 제한) 순서 목록 하나라 과하다. (c) `core/storage` DataStore — 목록 전체 쓰기라 결과는 (a)와 같고 모듈만 늘어난다.
- **B4 대기열 재개 시점.** (결정, Codex R1 B-2) iOS는 보드가 보일 때 · "다시 보내기"에서만 재개해 앱 재시작 뒤 보드를 열지 않으면 대기 건이 나가지 않는다. Android는 여기에 앱 시작 뒤 현재 사용자 확인 · 로그인 · 연결 복구를 더한다(대기열 절 "재개 시점"). 버린 안: iOS와 같게 보드에서만 재개 — 팔로워가 변경을 영영 못 볼 수 있다.
- **B5 업로드 제한 시간.** (a) `createFestiCoreHttpClient`에 `HttpTimeout`을 설치하고(기본값은 OkHttp와 같게 두어 다른 요청 동작 유지) 업로드 요청만 `requestTimeoutMillis = 60_000`(추천, iOS와 같음). (b) 플러그인 없이 OkHttp 기본에 맡긴다 — 코드는 줄지만 iOS 60초 총 제한과 다르다.

- **잠금화면 · 대표 깃발(라이브 액티비티 단계)**: iOS `LockScreenSettingsFeature` · `PinnedFlagPickerFeature`가 `BearerDomain` `fetchPinnedFlag` · `fetchFollowedFlags`를 쓴다(`LockScreenSettingsFeature.swift:96`, `PinnedFlagPickerFeature.swift:66 · 119`). 이 문서는 도메인 함수만 만든다(B7). 잠금화면 줄 · 대표 깃발 고르기 화면 · 저장(`PUT me/pinned-flag`, 이미 `FlR`에 있음) · 실제 잠금화면 표시는 라이브 액티비티 단계 문서가 정한다(마이 탭 설계 M5, 깃발 설계 F4-1). 기수 보드의 상태 변경이 팔로워 라이브 액티비티에 보이는 것은 서버 몫이라 이 문서와 겹치지 않는다.
- **푸시(P0)**: "팔로워에게 알림이 가요"는 서버가 팔로워에게 보내는 푸시다. 기수 쪽 앱 동작은 없다.
- **깃발 탭**: 깃발 상세 "오늘 계획"(`planRowsKeepBearerOrder`, 이미 옮김)은 기수가 저장한 순서를 읽기만 한다.
- **분석**: iOS 기수 화면에 이벤트가 없어 Android도 넣지 않는다. 생기면 `service/analytics/.spec/analytics.md` 표에 더한다.

## 검토 반영

- **Codex R1 B-1(high, 대기열 계정 격리 · 세션 묶기)**: 반영. iOS는 맨 앞 건 주인이 다르면 주인이 현재 사용자가 아닌 건만 버리고 현재 사용자 건은 남긴다(`BOX:117-125`) — 문서 문구가 "다른 계정 건을 모두 버림"으로 모호해 고쳤다. iOS는 사용자 확인(`BOX:110-117`)과 세션 읽기(`BRI:171`)가 따로라 그 사이 계정이 바뀌면 이전 사용자 건이 새 세션으로 나갈 틈이 있다. Android는 세션 → 사용자 → 세션 재확인 뒤 건 주인이 그 사용자일 때만 `expectedSessionId`로 묶어 보내고, 세션이 바뀌면 플러그인이 막아 `NeedsLogin`, 늦은 응답은 보드에 알리지 않으며, 계정 변경 때 작업을 취소한다(마이 탭 A1과 같은 방식). 대기열 절 "계정 격리 · 세션 묶기", BD3 테스트 3건.
- **Codex R1 B-2(medium, 재개 시점)**: 반영. iOS 재개는 보드 표시(`BBF:314-324`) · "다시 보내기"(`BBF:231-234 · 333-336`)뿐이고 앱 · 내비게이션 호출이 없다. Android는 앱 시작 뒤 사용자 확인 · 로그인 · 연결 복구에서도 재개하고, 보드 밖에는 표시를 두지 않으며 멈춤 상태는 로그인 · "다시 보내기"로만 잇는다. 대기열 절 "재개 시점", 쟁점 B4 결정, 위험 절, BD3 테스트 3건.
- **Codex R1 B-3(medium, 보드 재진입 · 연결 복구 시 최신 상태)**: 반영. iOS는 보드를 새로 열 때(`BBF:376`) · 다시 시도 · `Rejected`(`BBF:418-420`)에만 다시 읽고 포그라운드 · 연결 복구 · 웹소켓 재조회는 없다. Android는 여기에 포그라운드 복귀(`ON_START`)와 연결 복구 때 지금 보드를 유지한 채 다시 읽기를 더한다. 주기 폴링 · 웹소켓은 두지 않는다. 화면 1 "최신 상태 다시 읽기", BS4 테스트 2건.
- **Codex R2 B-4(medium, 계정 변경 시 라이브 스택의 기수 보드)**: 반영. iOS는 계정 데이터를 지울 때 축제 스택에서 `bearerBoard`를 지운다(`FCo:29-36` `clearAccountData`). Android `FestivalCoordinator.onAccountChanged()`는 지금 `ZoneMap` · `NotificationInbox` · `Crew` · `CrewCreate`만 지운다(`FCoA:291-304`). BC1에서 `FestivalRoute.BearerBoard`를 더하고 `accountChangeClosesBearerBoard`를 `FestivalCoordinatorTest`에 둔다. 화면 전환 표 · BC1 행.
- **Codex R2 B-5(medium, 응답 때 세션이 다르면 건 소실)**: 반영. 2xx로 반영이 확정된 건만 지우고(세션이 바뀌었으면 보드에 알리지 않음), 취소 · 결과 불명이면 원래 주인 건으로 남겨 그 주인이 다시 로그인하면 보낸다. 다른 계정 건도 버리지 않고 남긴다(iOS는 버림 `BOX:117-125` — Android가 다른 점). 다시 보내도 안전한 근거는 서버 `(userId, Idempotency-Key)` 24시간 응답 재생(`flags.service.ts:199-223 · 245`)과 `clientAt` 비교(같으면 반영 없이 현재 상태 `flag-rules.ts:301-310`, 이르면 `STATUS_STALE` `flag-rules.ts:177-181`), 대기열이 같은 키 · 같은 `clientAt`을 보관함(`BOR:11-19`). 대기열 절 "계정 격리 · 세션 묶기" 2 · 3 · 5번, BD3 테스트.
- **Codex R2 B-6(low, 만료 · 오래된 변경 폐기)**: 반영. iOS 대기열에는 만료가 없고, 서버는 날짜가 지나도 더 늦은 `clientAt`이면 받는다(`flag-rules.ts:177-181`). 기수 상태가 하루 단위라서(`BE` `BearerFlag.swift` · 재시작 KST 하루 한 번), Android는 서울 날짜가 다르거나 24시간(서버 멱등 보관 기간)을 넘은 건을 읽을 때 · 고를 때 버리고 `Rejected`와 같이 최신 상태를 다시 읽는다. 다른 계정 건의 기기 보관 기간도 하루로 묶인다. 대기열 절 "만료", BD3 테스트 3건.
- **Codex R3 B-7(medium, 시계 오차)**: 반영. iOS는 `clientAt`을 기기 시각으로 만들고 보정이 없으며(`BUI:96-98`), 서버의 미래 `clientAt` 거절(400 `VALIDATION`, `flag-rules.ts:171-176`)을 `InvalidRequest`로 받아 그 깃발 대기 건을 모두 버린다(`BRI:247`, `BOX:145-151`) — iOS에도 같은 구멍이 있다. Android는 기수 응답의 `Date` 헤더로 서버 시각 오프셋을 두어 `clientAt` · 만료를 정하고, 400이면서 `건 clientAt > 응답 Date + 5분`일 때만 시계 오차로 보아 대기 건을 버리지 않고 `clientAt`을 순서대로 당겨 같은 멱등키로 한 번 다시 보낸다(400은 멱등 기록 전이라 안전, `flags.service.ts:1101 · 1150`). 대기열 절 "시계 오차", BD3 테스트 6건.
