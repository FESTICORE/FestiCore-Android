# iOS 구조 맞추기 R6 설계 (모듈 구성 전수 정렬)

- 날짜: 2026-11-24
- 이슈: #196
- 기준: Android `develop` `3be4e22`, iOS `FestiCore-iOS/Projects` 작업 트리(읽기 전용)
- 결정(사용자): "전체 모듈 다 확인해서 iOS랑 똑같이 맞춰". R0~R5(`2026-11-23-ios-structure-alignment-design.md`)가 끝난 뒤 남은 모듈 · 폴더 차이를 전부 없앤다.
- 범위: R6a는 R0~R5와 같은 원칙(이동 · 이름 · 의존 · Koin 위치만, 로직 그대로)이다. R6b~R6d는 iOS에만 있는 모듈을 새로 만들고 사용처까지 옮기는 이식이라 동작이 생긴다. 각 PR이 어느 쪽인지 7절에 적는다.
- 이 문서는 설계만 담는다. 코드 수정은 각 PR 이슈에서 한다.

## 0. 근거 규칙

- R0~R5 문서의 이름 규칙(2.1)을 그대로 쓴다. iOS 폴더 이름을 소문자로, 앞 `FestiCore` · 뒤 `Domain`은 떼고, `Interface` · `Sources` 타깃은 `interface` · `sources` Gradle 모듈로 나눈다.
- 화면 패키지는 iOS `Sources/<화면>` 폴더 이름과 같게 둔다(`.claude/rules/feature.md:14`). 한 화면 안은 Contract · ViewModel · Screen을 한 패키지에 둔다(`.claude/docs/android-mvi.md:35-46`).
- 구현을 가진 모듈이 자기 Koin 모듈을 등록하고, assembly는 목록만 합친다(`.claude/docs/dependency-injection.md`).
- 라이선스는 Apache-2.0 · MIT · OFL만 바로 쓴다. 그 밖은 사람 승인을 기다린다(`CLAUDE.md` 규칙 12).
- 키 · 설정 파일은 추적하지 않는다. 토큰 · 개인정보는 로그 · 분석 이벤트에 넣지 않는다(`CLAUDE.md` 규칙 8).

## 1. 전수 대조

조사 방법: iOS `Projects/*/*`의 모든 폴더에서 `Derived` · `.xcodeproj`를 빼고 `.swift` 파일 수를 셌다(`Project.swift` 제외). `Interface` · `Sources` · `Tests` 하위 폴더와 `Project.swift` 의존을 열었다. Android는 `build.gradle.kts`가 있는 43개 모듈의 `src/main` · `src/test` 패키지와 파일을 셌다.

표기: 같음 / 이름만 다름 / 나눔 다름 / 폴더 다름 / iOS에만 / Android에만 / 대응 불필요(iOS 빈 모듈).

### 1.3 호스트 목록과 다른 점

- 새로 찾음: `Data/FestiCoreData`(빈 계층), `core/logger` 타입 이름, `core/network` 내부 폴더, `ui/animation` `Lottie/`, `app/navigation` 하위 폴더, `feature/{auth,web,festival}` 화면 폴더, `domain/{auth,timetable}` 폴더, `service/apiendpoint` · `service/festivalcatalog` 요청 파일 나눔, `service/pack` `PackSyncError` 파일, `MapApp` · `MapAppClient`가 iOS `FestiCoreLocationInterface`에 있다는 것.

R6a에서 문서를 고친다.

## 2. 결정 상세 (R6a 구조)

### 2.1 feature/onboarding 합치기

- `feature/onboarding/interface`의 `OnboardingRoute` · `OnboardingResult`를 sources로 옮기고 `feature/onboarding/interface`를 지운다. `feature/onboarding/sources` 폴더를 `feature/onboarding`으로 올린다(Gradle 경로 `:feature:onboarding`).
- 플러그인 `festicore.android.feature`. namespace가 `io.festicore.feature.onboarding.sources` → `io.festicore.feature.onboarding`으로 바뀌므로 `R` import(그림 4장)를 고친다.
- `app` · `feature/featureassembly`는 `:feature:onboarding:sources` → `:feature:onboarding`. 다른 feature가 이 모듈을 보지 않으므로 check-boundaries "feature는 다른 모듈의 sources를 의존하지 않는다"에 걸리지 않는다. 단일 feature 모듈을 다른 feature가 보지 못하게 하는 규칙을 더한다(3.2).

### 2.2 core/storage 나누기

| 모듈                     | 패키지                                | 내용                                                                                                                                                                                                                                                                                             |
| ------------------------ | ------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `core/storage/interface` | `secure/` · `shared/` · `onboarding/` | `secure/SecureStorage` · `SecureStorageException`, `onboarding/FirstInstallOnboardingStore`, `shared/{AppearanceModeStore,FestivalPackLocalStore,LiveBoardPreferenceStore,PendingDeeplinkStore,RecentSearchStore}`(iOS `Shared/*SharedKey`가 맡는 설정 값 자리). 공개 값 타입은 같은 파일에 둔다 |
| `core/storage/sources`   | 같은 하위 패키지 + `di/`              | `DataStore*` 구현 · `KeystoreValueCipher` · `coreStorageModule`(인터페이스 타입으로 등록). iOS `Factory/StorageFactory`는 Koin 역할이라 폴더 없음                                                                                                                                                |

- 지금 각 파일은 `interface X`와 `internal class DataStoreX`를 같이 둔다. 인터페이스 선언은 interface 모듈 파일로, 구현은 sources 파일로 글자 그대로 나눈다(R5 `service/device`와 같은 방식).
- 사용처(`app` 9 · `domain/{auth,festival,usernotification}/sources` · `service/{auth,device}/sources`)는 `:core:storage:interface`로 바꾸고 `core/coreassembly`만 sources를 본다. `iOS Database/AppDatabaseDependency`(SQLite)는 Room이 없으므로 빈 패키지를 만들지 않는다.

### 2.3 요청 파일 나눔 (service/apiendpoint · service/festivalcatalog)

iOS는 팩 요청만 `APIEndpoint/Festival/FestivalPackRequest`에 두고 목록 · 상세 · 라이브 · 깃발 팔로우 · 공식 소식 요청은 `FestiCoreFestivalCatalog/Sources/Endpoint`에, 내 일정 요청은 `NetworkFestivalScheduleService` 안에 둔다.

| Android `FestivalRequest` 함수          | 호출처                                                                | 목표                                                                                       |
| --------------------------------------- | --------------------------------------------------------------------- | ------------------------------------------------------------------------------------------ |
| `packVersion` · `packChanges`           | `domain/festival/sources` ZoneMap · PackChanges Repository            | `service/apiendpoint/festival/FestivalPackRequest`                                         |
| `list` · `live` · `flags` · `instagram` | `service/festivalcatalog`만                                           | `service/festivalcatalog/endpoint/Festival{List,LiveBoard,FlagFollow,OfficialNews}Request` |
| `mySchedule` · `replaceMySchedule`      | `NetworkFestivalScheduleService`만                                    | `endpoint/FestivalScheduleRequest`(iOS는 서비스 파일 안 — 파일만 나눈다)                   |
| `detail`                                | `NetworkFestivalCatalogService` + domain Crew · FlagDetail Repository | 쟁점 F8                                                                                    |

### 2.4 service/config

- `service/config`(단일 모듈, `festicore.android.library`) `FirebaseConfiguration.configure(context)`: `BuildConfig`로 받은 Firebase 값(푸시 설계 `2026-11-22-push-device-android-design.md` 96행의 4개 값)이 모두 있을 때만 `FirebaseApp.initializeApp(context, FirebaseOptions)`, 없으면 로그 한 줄만 남기고 아무것도 하지 않는다(iOS `FirebaseConfiguration.swift:14-27`과 같은 동작). 값은 `app`이 넘긴다(service는 app `BuildConfig`를 모른다).
- `google-services` Gradle 플러그인 · `google-services.json`은 쓰지 않는다(파일을 추적하지 않는 규칙 8과 CI 빌드 때문). 의존은 `firebase-common`(BOM)만.
- `FestiCoreApplication.onCreate`가 `FirebaseConfiguration.configure` → (R6b) `FestiCoreAnalyticsConfiguration.configure` 순서로 부른다(iOS `AppDelegate+Configuration.swift:16-17`).
- Koin 등록 없음(iOS도 `enum`의 정적 함수). 그래서 serviceassembly 목록에 넣지 않는다.

## 3. 새 모듈 의존 방향 · check-boundaries

### 3.1 의존 방향 (iOS `Project.swift` 근거)

```
service/config            → firebase-common                                   (iOS FestiCoreConfig → firebaseCore)
service/analytics/interface → (없음)                                          (iOS Interface → TCA만)
service/analytics/sources → service/analytics/interface · core/logger · sentry-android · mixpanel-android
core/location/interface   → (없음)
core/location/sources     → core/location/interface · androidx.core(LocationManagerCompat)
core/storage/interface    → (없음)
core/storage/sources      → core/storage/interface · datastore
domain/bearer/interface   → (없음)
domain/bearer/sources     → domain/bearer/interface · service/apiendpoint · service/{auth,device,pack}/interface · core/network/interface
feature/bearer/interface  → domain/bearer/interface
feature/bearer/sources    → feature/bearer/interface · domain/bearer/interface · domain/festival/interface · ui/*

feature/{festival,profile}/sources → + core/location/interface (R6c) · core/storage/interface (쟁점 F2)
```

- iOS `Feature/Bearer`는 `.core(.utility)`를 본다. Android는 R6d에서 쓰는 곳을 확인하고, 순수 문자열 도우미면 `feature/bearer/sources/common`에 둔다.

## 6. 기능 영향

### 6.1 analytics (R6b)

- `service/analytics/interface`: `event/`(`AnalyticsEvent` sealed — `signUp` · `screenView` · `uiAction` · `flagFollow` · `timetableAction` · `packSync` 등, `AnalyticsScreen` · `AnalyticsButton` · `AnalyticsProvider` · `FlagFollowData` · `TimetableActionData` · `PackSyncData`), `usecase/AnalyticsUseCase`(`registerBaseProperties` · `identify` · `track` · `reset`). iOS처럼 UseCase를 service에 둔다(domain이 아님).
- `service/analytics/sources`: `configuration/{FestiCoreAnalyticsConfiguration,SentryConfiguration,MixpanelConfiguration}`, `log/SentryLogSink`(`core/logger` `FestiCoreLogSink` 구현, Sentry가 켜졌을 때만 추가), `usecase/AnalyticsUseCaseImpl`, `di/ServiceAnalyticsModule`. iOS `Trace/FestiCoreTracedView`는 사용처가 1곳이다 — R6b 착수 때 그곳을 보고 정한다(쟁점 F3).
- 호출처 이식(iOS `analyticsUseCase.*` 호출 기준): app `AuthCoordinator` 2 · `AccountCoordinator` 2 · 시작 1, feature `Login` 1 · `FestivalFeature` 4 · `FestivalFlagDirectory` 1 · `FestivalFlagFeature` 1 · `FestivalFlagDetailFeature` 1 · `AccountSettings` 2 · `Profile` 1 · `Timetable` 4 · `Web` 1. ViewModel이 생성자로 `AnalyticsUseCase`를 받는다. Android 화면이 아직 없는 호출처는 그 화면 이식 PR로 넘긴다.

### 6.2 location (R6c, 사용 기능 포함)

- `core/location/interface`: `entity/{LocationCoordinate,LocationClientError,LocationAuthorization,WalkingDuration,WalkingPlace}`, `client/{LocationClient,MapAppClient(+MapApp),AppleMapsClient 대응}`. iOS `Mock*Client`는 Android 관례대로 테스트 fake로 둔다.
- `core/location/sources`: `client/{PlatformLocationClient(LocationManagerCompat),PackageManagerMapAppClient,…}` · `client/NearestPlace`(iOS 그대로) · `di/CoreLocationModule`. 권한 `ACCESS_COARSE_LOCATION` · `ACCESS_FINE_LOCATION`은 이 모듈 매니페스트에 둔다.
- 팩 상세: `feature/profile/sources/packdetail/MapApp.kt`의 `MapApp` · `MapAppClient` · `PackageManagerMapAppClient`를 그대로 `core/location`으로 옮긴다. 동작 변화 없음(`<queries>`는 app 매니페스트 그대로).
- 라이브 보드 귀가 "가는 길": iOS `FestivalFeature+HomeWalk.swift`(권한 확인 → 현재 위치 → 가장 가까운 역 · 정류장 → Apple 지도 도보 ETA → 길 안내)를 `LiveBoardViewModel` 귀가 상태(`home`, 라이브 보드 설계 D6 경계)에 옮긴다. Android에는 Apple 지도가 없어 도보 ETA를 기기에서 계산할 수 없다. 추천: ETA는 서버 `transit.walkMinutes`를 계속 쓰고, "가는 길"은 지도 앱 인텐트로 연다(쟁점 F4). `walkingDuration`은 Android 구현에서 `null`을 돌려 iOS의 "계산 못 함 → 서버 값" 경로를 그대로 탄다.
- 개인정보: 위치는 기기 안에서만 쓰고 서버 · 로그 · 분석으로 보내지 않는다(iOS와 같음). Play Console 데이터 보안 양식 · 개인정보처리방침의 위치 항목 갱신은 **사람이 한다**.

### 6.3 기수 (R6d)

- 범위: iOS `Feature/Bearer` 4,797행(Board · Plan · Register · RoleChoice · Profile · Claim 6흐름, Interface Delegate 5) · `Domain/BearerDomain` 2,089행(Entity 7 · UseCase · Repository · `StatusOutbox` 재시도 · 사진 인코딩 · DTO 3 · Mapper 2), 관련 `ui/sharedui` `FCBearerChoiceSheet`, app `Navigation/Bearer/BearerEntryCoordinator`, `service/apiendpoint` `Flag` 요청(claim · register · bearerFlags · pinnedFlag · follows · 사진 업로드), 마이 탭 기수 카드 · 내 깃발(마이 탭 설계 M7), `Profile/LockScreen` 대표 깃발.
- 화면 · 상태 · 업로드 · 오프라인 재시도 설계가 커서 **R6d 착수 전에 별도 화면 설계 문서(`.claude/docs/specs/<날짜>-bearer-android-design.md`)를 쓴다**. 이 문서는 모듈 자리(`domain/bearer/{interface,sources}` · `feature/bearer/{interface,sources}`)와 의존(3.1)만 정한다.

## 10. 확인 못 한 것

- iOS `FestiCoreTracedView` 사용처 1곳의 화면과 측정 이름.
- `NetworkFestivalCatalogService.festivalDetail`의 캐시 여부(F8).
- iOS `BearerStatusOutbox`가 기록을 어디에 저장하는지(`BearerOutboxRecordDTO`), `Feature/Bearer`가 `core/utility`에서 쓰는 것.
- Sentry Android · Mixpanel Android 최신 버전과 POM 라이선스(PR에서 다시 확인), Sentry Android 기본 계측이 요청 헤더를 담는지.
- `service/analytics/sources`의 Mixpanel 초기화가 `Context`를 요구하므로 Koin 등록과 `Application` 초기화 순서.
- Android `androidTest`(UI 테스트) 대응 여부 — iOS `App/Tests/UITests` 6개. 이 문서 범위 밖.
- 이 문서는 Codex 교차 검토를 거치지 않았다.
